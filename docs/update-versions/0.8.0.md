# v0.8.0 - a Terminal page and scheduled Docker cleanup

**Released:** 2026-10-22 · **Tag:** `v0.8.0`

This release adds the two operator surfaces that were missing from the server
page: a first-class **Terminal** in the sidebar for server and container shells,
and a configurable **Docker cleanup** schedule with execution history.

## Update

```bash
meghify update
```

The panel applies migration `007_docker_cleanup` automatically. It adds
`docker_cleanup_settings` and `docker_cleanup_runs`; no existing table changes
and no manual SQL is needed.

## Terminal

- **Terminal** is now a top-level sidebar item (admins). It lists every server
  and every **running container** across those servers, with a filter for
  names and images.
- A row opens either the server's shell or an interactive `exec` shell inside
  the selected container. The application page's terminal still works and now
  uses the same toolbar.
- **Idle terminals stay connected.** The panel sends a WebSocket ping every
  20 seconds, so a reverse proxy or browser does not treat a quiet shell as
  dead. If the connection still drops (laptop sleep, network change), the
  browser reconnects with exponential backoff and shows the state.
- **Terminal preferences.** Pick **Midnight**, **Graphite**, **Solarized**,
  **Dracula** or **Paper**, and increase or decrease the font size from the
  toolbar. Preferences are stored in the browser and shared by every terminal.
  There is also a manual **Reconnect** button.
- Shell sessions no longer disappear after a few idle minutes on hosts behind
  a proxy. Reaching the panel through HTTPS needs no extra configuration: the
  page uses `wss://` automatically.

## Docker cleanup on the server page

The local server page has a new **Docker cleanup** section:

- **Scheduled maintenance** — enable or disable the schedule and set a
  five-field cron expression. Daily at midnight, every six hours and weekly
  are one-click presets.
- **Trigger** — run on every schedule, or only when the host's disk usage is
  above a configurable threshold (1–99%).
- **Advanced cleanup** — opt into removing unused panel-labelled volumes and
  networks. Both are off by default because an unused volume may still contain
  data you need. Application images can keep the configured `IMAGE_KEEP`
  rollback window, or the pass can remove retained images and keep only what
  current containers reference.
- **Recent executions** — successful and failed runs with their trigger,
  timestamp, duration, reclaimed storage and error. Scheduled runs are
  durable jobs, so a panel restart does not lose the next occurrence.
- **Run cleanup** executes the saved options immediately. The dashboard's
  existing **Free up space** button intentionally runs only the safe default
  pass, so a schedule setting cannot turn a routine click into a volume prune.

Only resources labelled `meghify.managed=true` participate in the optional
volume and network sweep. Unrelated Docker projects and volumes are left
alone. The build-cache volume itself stays because it is referenced by the
stopped build sandbox; the cache inside it is still bounded by
`BUILD_CACHE_KEEP`.
