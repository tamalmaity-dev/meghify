# 0.6.4 — The cache bound follows the build, obsolete helpers go

## Why

The first 0.6.3 deployment on a production VPS showed both remaining gaps at
once:

- The storage card reported the sandbox build cache at **9.9 GB mid-build and
  9.1 GB after** — over the configured 8g bound. The bound was enforced only
  by the hourly `gc` job, so a busy run of builds could overshoot the ceiling
  between two passes.
- The largest-items list still carried the **helper images of every previous
  release** (`meghify-helper:v0.6.1`, `v0.6.2` next to `v0.6.3`) — panels
  upgraded in place had no reason ever to drop them.

## What's new

### The build cache bound is enforced after every release

Right after the image trim, the release itself prunes the build cache on the
engine and inside the sandbox back to `BUILD_CACHE_KEEP`. The prune keeps the
most recently used records first — exactly the cache the next build reuses —
so it costs a short pause, not the warm cache. The log line appears only when
it actually reclaimed at least 64 MB:

```
[ok] build cache bounded to 8.0GB (~1.2GB reclaimed)
```

### Superseded helper images are removed by every cleanup pass

Cleanup now removes every image from the helper's own repository that is not
the helper the running panel uses: old `meghify-helper:v0.6.x` tags after an
upgrade, in the hourly `gc` and in **Free up space** alike. The active helper
is protected precisely — a pinned `BUILD_HELPER_IMAGE` survives untouched —
and images a live build still serves are refused by the engine and skipped.
Application repositories and anything the operator brought themselves are out
of scope, as before.

## Updating

```bash
meghify update
```

The first cleanup pass after boot drops the old helper versions; expect a
`docker cleanup reclaimed storage` log line for about the size of one helper
image per previously installed release.
