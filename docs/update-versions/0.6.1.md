# v0.6.1 — releases that cannot orphan a dead app; build-time service DNS

**Released:** 2026-10-18 · **Commit:** [`488b6f0`](https://github.com/tamalmaity-dev/meghify/commit/488b6f0) · **Tag:** `v0.6.1`

Two deployment failures report v0.6.0 at odds with what Coolify produces on
the same VPS: the build kept the CPU at 72% while the application was "still
deploying", and the application domain answered the proxy's bare
`404 page not found` while nothing was running. Both are the same failure —
a release step that can deploy a container that is already dead without
telling anyone — plus a real build-time gap against Coolify's behavior.

## Update

```bash
meghify update
```

## What changed

### Releases are confirmed before the old deployment is retired

The rolling release now treats the first seconds after the replacement starts
as a contract:

- with a health check configured, failure prints the container's output into
  the deployment log before the revert happens;
- **without** a health check, a container that exits dead-on-arrival (missing
  env var, OOM kill, broken start command) or shows restarts inside the
  startup window fails the deployment, the container's recent output is
  copied into the log, and the previous deployment keeps running.

Before this, a container that died at startup was still "released": the panel
reported success, the app status showed "running", and the domain kept
answering Traefik's bare `404 page not found` while nothing ran. Coolify and
Dokploy both fail the deployment instead; that is now our behavior too.

### Builds resolve sibling services by name

A build process runs without user-defined-network DNS, so an app whose
`next build` prerenders against a database service failed to resolve the
service's host. Dockerfile and nixpacks builds now receive the
`--add-host name:ip` entries of the application's private network — the same
mapping Coolify assembles before every build.

### Nixpacks builds use Coolify's two-step invocation

`nixpacks build PATH --out` only generates the Dockerfile; the panel then runs
the `docker build` itself (with the host entries, image labels, and the
`--cache-key` mapped to the application — nixpacks' BuildKit cache mounts keep
keying across deployments). Previously `nixpacks build` hid the docker build
inside the binary, which made both features impossible.
