# v0.3.2 — pull reliability on Docker 29

**Released:** 2026-10-17 · **Commit:** [`f867625`](https://github.com/tamalmaity-dev/meghify/commit/f867625) · **Tag:** `v0.3.2`

Docker Engine 29 uses the containerd image store by default, and there a pull
of a multi-platform image carrying build attestations can abort at the final
layer commit (`failed commit on ref … rename ingest → blobs: no such file`).
On such engines the build-helper image could fail to pull, and the build fell
back to host tools that most servers don't have. Two changes fix that.

## Update

```bash
meghify update
```

or re-run the installer. No database changes.

## What changed

- **Pulls retry once.** By the time a pull fails at the commit stage every
  layer blob is already written to the content store, so the retry finds it
  all cached and completes in seconds. This applies to the build helper, the
  terminal helper and Docker Image deployments alike.
- **The helper image publishes without provenance/SBOM attestations**, which
  removes the duplicate manifests that trip the containerd layer-commit path
  during a pull.

## Notes

- If a helper pull still fails twice, the deployment log says so and the
  pipeline falls back to host tools (an install that carries them keeps
  working).
