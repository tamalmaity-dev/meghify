# v0.6.0 — isolated build sandbox; builds can no longer take the server down

**Released:** 2026-10-18 · **Commit:** [`f9543df`](https://github.com/tamalmaity-dev/meghify/commit/f9543df) · **Tag:** `v0.6.0`

Builds are the heaviest thing a small VPS ever runs. A runaway `npm ci` or a
hung `docker build` previously competed with the panel, the proxy and every
running container for the whole machine — and if the panel died mid-build, the
deployment stayed "building" forever and blocked every later deploy. This
release moves builds into their own resource-limited sandbox and gives every
deployment a hard deadline.

## Update

```bash
meghify update
```

No schema changes.

## What changed

### The build sandbox (Docker-in-Docker)

Dockerfile, nixpacks and railpack builds now run inside an isolated,
resource-limited Docker daemon (`meghify-buildd`, image `docker:29-dind`,
cache volume `meghify-build-cache`, network `meghify-build`) instead of
against the engine that runs the panel and the applications:

- the build daemon is capped with `BUILD_CPU_LIMIT` / `BUILD_MEMORY_LIMIT`;
  unset, **half of the node** is reserved for builds (at least 1 core / 1 GiB,
  at most 4 cores / 8 GiB, logged at sandbox creation);
- the finished image is transferred to the host engine (`docker save` →
  `docker load`, compressed) before the rolling release, so releases still
  happen where the containers run;
- compose stacks keep the engine socket — `docker compose up` must create the
  application containers on the host engine.

`BUILD_SANDBOX` selects the behavior: `auto` (default) falls back to the
legacy socket-mounted helper when nested Docker is not permitted, `on` makes
a sandbox failure an error, `off` disables the sandbox. The model matches what
Coolify and Dokploy do — a disposable builder with its own resource envelope —
without needing a second server.

### Deployments get a hard deadline

`DEPLOY_TIMEOUT` (default **30m**) bounds build, image transfer, release and
health checks. When it fires, the helper container is removed — killing the
build process — and the deployment fails with a clear message instead of
holding the queue forever.

### Kill build

A running deployment can be stopped from the UI: open the build output and
press **Kill build** (`DELETE /api/deployments/{id}`). The build context is
canceled, the helper container removed, the deployment marked canceled and the
application's status restored from its actual container.

### Startup recovery

If the panel is killed or the VPS reboots mid-deployment, startup now marks
the in-flight deployment **canceled** ("interrupted by a panel restart"),
restores the application's status, removes orphaned build helpers and deletes
half-created rolling-release containers. A stuck deployment row can no longer
block later deploys. (Dokploy does the same at boot.)

### Nixpacks builds get Node 22 by default

Nixpacks falls back to the end-of-life Node 18 whenever `package.json` has no
`engines` field, which breaks today's Next.js dependencies. Builds now pass
`NIXPACKS_NODE_VERSION=<BUILD_DEFAULT_NODE_VERSION>` (default **22**) unless
the application sets it, and every `build`-scope environment variable reaches
nixpacks as `--env`.

## Upgrading notes

- The first deployment after the upgrade pulls `docker:29-dind` (~250 MB) and
  starts the sandbox; it is reused from then on.
- Sandbox limits are read when the container is created. After changing
  `BUILD_CPU_LIMIT` / `BUILD_MEMORY_LIMIT`, remove the container
  (`docker rm -f meghify-buildd`) so it is recreated with the new envelope.
- Long builds that used to run past 30 minutes need `DEPLOY_TIMEOUT=1h` (and
  the same in your service environment).
