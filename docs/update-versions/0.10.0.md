# v0.10.0 - Automatic updates and a small-VPS resource guard

**Released:** 2026-11-27 · **Tag:** `v0.10.0`

This release adds an update card to Settings that can apply a release from the
panel, and retunes Resource Guard so a single runaway core on a small VPS is
caught instead of ignored.

## Update

```bash
meghify update
meghify restart
```

Migration `010_resource_guard_defaults` is applied automatically. It only
rewrites the untouched default policy; an operator who already saved Resource
Guard settings keeps them.

## Updates in Settings

Settings now shows the installed version and the latest published release.

- **Update available** - the latest tag, a **Release notes** link and an
  **Update now** button for admins.
- **Up to date** - a green confirmation.
- **Check failed** - a muted message; the rest of the page still works.
- **Development build** - update checks are informational only.

The check is cached server-side for one hour (five minutes after a failure), so
opening Settings does not spend GitHub's unauthenticated request budget. The
refresh button forces a check, but no more than once a minute.

### Update now

On a systemd install the button starts the installed CLI:

```text
POST /api/update/apply
  -> systemd-run --unit=meghify-update --collect --no-block meghify update
       -> download the release
       -> swap the binary (keeps meghify.old)
       -> systemctl restart meghify
       -> health-check, roll back on failure
```

The updater runs in a transient systemd unit because the panel service uses the
default `KillMode=control-group`: a plain child process would be killed by the
`systemctl restart` it performs. The browser polls `/api/version` every three
seconds and reloads once the new version answers.

Safety:

- admin only;
- a confirmation step before anything starts;
- refused while an update is already running (ten-minute lockout);
- refused when the install cannot update itself.

Docker installs are refused with a clear message: the panel container is
distroless and has no systemd or CLI. Update those from the host with
`meghify update`.

The server needs `systemd-run`, `/usr/local/bin/meghify` and the
`meghify.service` unit. The standard installer provides all three.

## Resource Guard defaults

The previous policy (90% of host CPU for ten minutes) could never fire on a
two-core VPS: one pegged core is only about 50% of the host, so a runaway
single-core process was never caught.

| Setting | Before | Now |
|---|---|---|
| Application CPU | 90% of host, 600s | **40% of host, 600s** |
| CPU action | throttle to 50% | **throttle to 25%** |
| Application memory | 90% of limit, 300s | **60% of limit, 300s** |
| Host memory emergency | 95%, 120s | **90%, 120s** |
| Start grace | 300s | **60s** |
| Cooldown | 900s | 900s |
| Sampling interval | 30s | **10s** |

The 40% threshold sits just below one core on a two-core host, so a container
that saturates one core for ten minutes is throttled to a quarter of the host
instead of being left alone. Existing application overrides are unchanged.

## Migration and compatibility

- New defaults apply to fresh installs and to installs that never saved a
  policy.
- The migration matches the exact old default signature, so a customised policy
  is never overwritten.
- Applications, domains, nodes, cleanup schedules and routing files are
  unchanged.
