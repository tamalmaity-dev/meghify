# v0.9.0 - Resource Guard

**Released:** 2026-10-22 · **Tag:** `v0.9.0`

This release adds a host-safety backstop for runaway application containers.
Applications can still carry hard per-container CPU and memory limits; the
Resource Guard watches those limits and the host over time and acts when usage
stays dangerously high instead of reacting to a short spike.

## Update

```bash
meghify update
```

The panel applies migration `008_resource_guard` automatically. It adds the
panel-wide policy, per-application overrides and a three-month action history.
Existing applications are protected by default; no manual SQL is required.

## What the guard does

The guard samples every managed application container every 30 seconds. It
ignores short spikes and only acts after the configured sustained duration.

| Metric | Default threshold | Default action |
|---|---|---|
| Application CPU | 90% of total host CPU for 10 minutes | throttle to 50% of host CPU, notify |
| Application memory | 90% of the container limit for 5 minutes | stop the container |
| Host memory emergency | 95% of host RAM for 2 minutes | stop the largest protected application on that server |

- **CPU is measured against the host**, not one core, so a 4-core server at 90%
  means about 3.6 cores. A per-application threshold can override it.
- **Memory is measured against the container limit** when one is configured;
  with no limit it is measured against host RAM. The host-memory emergency
  covers pressure caused by several applications at once.
- **A memory stop is a real manual stop**: the container status becomes
  `stopped`, Docker's restart policy does not bring it back, and the panel does
  not restart it automatically.
- **A CPU throttle is temporary**: the live container gets a lower CPU cap and
  an event is recorded. The saved limit returns on the next deployment, or use
  **Apply limits now** on the Runtime tab to clear it immediately.
- The guard does not target the panel, proxy, build sandbox, databases or
  services, and it skips applications that are deploying or inside the start
  grace period.

## Configure it

Open the **local server page → Resource protection** (admin only). The policy
is panel-wide and applies to application containers on every managed server.
The page also shows the latest actions with the observed value, threshold and
result.

Each application's **Runtime** tab has a **Resource protection** card:

- opt the application out, or use the panel defaults;
- override CPU and memory thresholds;
- choose `notify`, `throttle` or `stop` for CPU, and `notify` or `stop` for
  memory.

CPU and memory limits remain editable in the Runtime card. Saving them now
pushes the new limits to a running container immediately where the engine is
reachable; **Apply limits now** forces the saved values onto the current
container without a redeploy.

## Scope and behavior notes

- The guard currently targets the final container created by the panel's
  Dockerfile and build-pack paths. Docker Compose stacks are managed as a stack
  and are not yet individually guarded.
- Notifications appear as toast events on an open application page and in the
  durable action history. Email, Telegram and webhook delivery are not part of
  this release.
- The action history is pruned after 90 days by the existing maintenance job.
- CPU and memory limits are the first line of defense. The guard is a backstop,
  not a replacement for cgroups: a hard memory limit stops a single container
  from consuming the entire host before a sampled check can run.

## Validation

The release adds tests for the migration, settings round-trips, event history
and pruning, threshold/duration evaluation, grace/cooldown handling, largest-
application selection, CPU throttling math and the complete memory-stop,
CPU-throttle and host-emergency action paths against a fake engine.
