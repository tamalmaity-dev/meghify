# v0.7.1 - quieter dashboard, retire the old Coolify helper

**Released:** 2026-10-21 · **Tag:** `v0.7.1`

This patch fixes two things visible on a small VPS: opening the dashboard could
cause a CPU spike while Docker measured its stores, and an old
`coollabsio/coolify-helper:1.0.17` image from pre-v0.3.1 releases was never
removed.

## Update

```bash
meghify update
```

No schema changes.

## Dashboard CPU spikes

The Docker storage card calls Docker's `/system/df` endpoint. That endpoint
walks every image layer, volume and build-cache record in the engine. On a
small node with a large build cache, that work can consume a visible CPU slice.
Previously it ran:

- whenever the dashboard mounted and its cached query had expired, and
- every minute while the dashboard remained open.

The server now caches one measurement for **15 minutes** and serializes
concurrent scans. The card shows the measurement time, refreshes every 15
minutes, and the **Refresh** button forces a new scan immediately. `Free up
space` also clears the cached measurement so the result is reflected at once.

This does not change the machine CPU or memory samples; appending those samples
is cheap. It removes the expensive Docker store walk from routine dashboard
rendering.

## Old Coolify helper removed

Meghify used `coollabsio/coolify-helper:1.0.17` before v0.3.1. Upgrades moved
builds to Meghify's own helper image, but the old tagged image stayed in the
Docker store and appeared in **Largest items** (about 621 MB). Cleanup now
removes tags from that retired repository during the hourly GC, startup cleanup
and **Free up space**. Docker still refuses to remove an image used by any
container, so an image belonging to a live or stopped Coolify container is
left alone.

## Why memory can look high

The Memory tile is **host-wide**, not just the Meghify process. It includes the
panel, the host Docker daemon, the build sandbox (`docker:29-dind`), the proxy
and every application container. The 7.5 GB build-cache volume is disk usage;
it is not the memory figure.

The build sandbox stays running between deployments so the next build does not
pay the Docker-in-Docker startup cost. If memory is tight on an 8 GB node, it
can be stopped manually when no build is running:

```bash
docker stop meghify-buildd
```

The next deployment starts it again automatically. The UI now calls this out
under the machine metrics.
